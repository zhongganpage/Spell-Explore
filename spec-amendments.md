# Spell-Explore — spec amendments

this file records the implementation clarifications and deviations from
planning-ideas-no-push.md — the locked spec, authoritative, never edited. every amendment
below is a runtime clarification: a decision about how the protocol is actually
executed. none of them changes the acceptance thresholds (≥2/3 swarm AND ≥2/3
BCD) or the 138-minute round budget. where this file is silent, the spec
governs.

| amendment | spec says | implementation does | reason | rule file |
|---|---|---|---|---|
| spec updated in place (2026-08-10) | the locked spec carried 9/9 + 3/3, 0/9 + 0/3, a ~9 swarm | the locked spec now carries the amended numbers (3/3 + 3/3, 0/3 + 0/3, a 3-worker swarm); the numeric rows below are the historical record of the deviation | the user decided to update the locked spec in place | planning-ideas-no-push.md |
| config schema | config.toml carries the per-phase budgets as machine-readable tables — `[round] budget_ms`, `[subagent.timeouts.*]`, `[subagent.timeline]`. | config.toml holds only real Kimi Code keys — `[background] max_running_tasks`, `[subagent] timeout_ms = 0`, `[secondary_model] model`; the per-phase budgets live in rules/timekeeping.md and the Coordinator enforces the windows operationally via TaskStop. | the invented tables are not Kimi Code config keys; the runtime ignores them, so they were dead weight. | rules/timekeeping.md |
| secondary-model mechanism | worker profiles route to the secondary model by `model_preference: secondary` alone. | routing needs the env flag `KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=1` (or the master flag) and a live-config alias — `[secondary_model] model = "moonshot-cn/kimi-k2.6"` (config.toml) — present in the live config's `[models]`. the panel's workerD does not route through this mechanism — see the workerD exterior reviewer row. | the runtime gates secondary-model routing behind the flag; without it every worker runs the primary model. | protocol/config.toml |
| workerD exterior reviewer (2026-08-10) | workerD is external — a reviewer on a different provider. | workerD runs through the configured exterior reviewer X — `X_PROVIDER` / `X_MODEL` / `X_ACCESS` (api: a provider API env var; codex: the local Codex CLI; modules/providers.md) — invoked by the Coordinator (an api call or `codex exec`), never a spawned subagent; the model the provider actually returned is recorded per panel row; when X is unavailable or shares the primary's provider family, workerD falls back to an internal reviewer and the reduced diversity is recorded with a confidence downgrade; a failed invocation is retried once; the vote at 118–138 is a second invocation with a consolidated prompt. | independence must be a real external call, not routing: the secondary-model mechanism depended on an experimental flag read at process start and silently fell back to the primary model. | modules/providers.md, rules/selector.md §3, worker-d-external.md |

| mixed-verdict rule | accept needs ≥2/3 swarm AND ≥2/3 BCD accept votes; accept-core needs ≥2/3 of both on accept-core. | when both gates pass their ≥2/3 threshold on accept-or-better but at different levels (e.g. swarm ≥2/3 accept, BCD only ≥2/3 accept-core), the route gets the weaker common verdict — accept-core, banked as a reduced route. | a split-level vote is not full acceptance; the salvageable core is still a genuine, correctly-proven contribution. | rules/selector.md |

| Producer backpressure and the route queue | each fresh summary is handed to the Producer and paired as it arrives. | the Producer applies backpressure when the Selector is busy: new summaries wait in a pairing queue, and carried reviews own the critical path in rounds ≥ 2 — a new review starts only if a full 75-min review fits. | the Selector runs two panels at a time; unpaired summaries queue instead of piling onto the critical path. | rules/core-loop.md |
| working-swarm write targets | the working swarm transforms the decomposed fragments into the single qmd file. | the working swarm writes per-fragment files plus a qmd-index while working, then assembles them into the single qmd file — the single qmd file itself is unchanged: one file at `formalizer/single.qmd`. | concurrent swarm workers need conflict-free write targets; the qmd-index keeps the assembly deterministic. | rules/formalizer.md |
| milestone is Lean-led | milestone = 9/9 + 3/3 with the accepted routes achieving the locked goal. | "achieving the goal" is verified on the dependency graph — the goal node reachable from `[Formalized]`/`[Hired]` assumptions; 3/3 + 3/3 is the presentation bar; non-unanimous reachability goes to the user for a decision. | green lean code in the reliable idea set is the only un-overturnable evidence; the graph is the operational check. | rules/coordinator.md |
| environment preflight | the round starts with the round-1 goal setup, then the clock. | at every round start the Coordinator runs an environment preflight — `lean --version`, qmd-prover availability, agent-profile discovery — before the clock starts. | a missing lean/qmd-prover or a wrong profile would fail the round mid-flight; fail fast instead. | rules/coordinator.md |
| single-writer file ownership | every worker writes its artifact at an assigned path, versioned. | each file has a single owner — only its owning role writes it; everyone else reads, and writes go to their own versioned files (recovered agent output is persisted by the subcoordinator). | concurrent background agents would corrupt shared files; single-writer keeps the artifact rules verifiable. | rules/core-loop.md §8 |
| canary placement | the canary gate rides each panel's review batch. | the canary is announced to the panel's B/C/D — they must report what they detect; at the swarm stage the canary is optional and unannounced. | the B/C/D window is short and fixed, so the announced canary keeps the gate verifiable; an unannounced swarm canary checks vigilance without inflating the panel load. | rules/selector.md |
| cut reports are re-queued | a phase that reaches its window end is cut and its partial output recorded; a partial report does not move on to the linter. | a report cut at the 20–45 window end is versioned as partial output and re-queued for the next round's Producer, not dropped. | the partial report holds real material; re-queuing preserves it while keeping the round's atomic close. | rules/core-loop.md |
| decision-swarm size | the decision swarm has ~9 workers; acceptance needs ≥2/3 of them. | the decision swarm is 3 workers — odd, so no tie — and ≥2/3 of 3 = 2 of 3 agree. | the smallest odd swarm that keeps the ≥2/3 double gate and the quality ranking while halving the round's agent load. | rules/selector.md |
| milestone consensus | milestone = 9/9 + 3/3 with the accepted routes achieving the locked goal. | milestone = 3/3 + 3/3 with the accepted routes achieving the locked goal — full consensus of the 3-worker swarm and the 3 BCD reviewers. | the milestone bar scales with the swarm: full consensus is now 3/3 + 3/3. | rules/coordinator.md |
| steering trigger | two consecutive rounds of total rejection (0/9 swarm, 0/3 BCD) trigger the steering report. | the trigger is two consecutive rounds of total rejection — 0/3 swarm and 0/3 BCD. | the trigger scales with the swarm size. | rules/coordinator.md |
| Producer two phases | the Producer pairs a fresh summary with its complement and one report worker writes the idea report. | the Producer runs two phases: phase 1 has two report workers, each pairing a triple of 3 fresh summaries (with its complement) into one idea report; phase 2 is the route writer — gated on (Creator phase 2 on AND accepted routes exist) — which revises accepted routes and receives the 2 lowest-goal-frontier leftover summaries. | two report workers keep one route on the critical path while the second works the pipeline; the route lane gives accepted routes a revision path without stealing the critical path. | rules/core-loop.md |
| Creator phase-2 split | phase 2 mines stale material, the reliable idea set and the fragment region with n idea-workers. | from round ≥ 2, when the pool has content, phase 2 runs split: 2 graph workers (active only when dependency-graph.json has nodes — they write bridging-lemma summaries from the graph) plus 2 regular miners. | the dependency graph is a distinct structured search surface; bridging-lemma summaries exploit it directly. | rules/core-loop.md |
| BCD worker rules | the BCD reviewers vote at the swarm stage with the ≥2/3 threshold. | the BCD reviewers keep ≥2/3 of 3 = 2 and add fixed worker duties: proof-step ledger, assumption audit, counterexample duty, evidence tie-in, boundary sweep, and a fixed verdict format. | explicit per-reviewer duties make the BCD reviews verifiable and their verdicts comparable. | rules/selector.md |
| PI handover | the PI of a route persists across rounds to defend it. | when a revision of an accepted route is accepted, the new PI — the Producer phase-2 route writer — writes the new version and marks the old superseded; the Coordinator records the current-defender-PI pointer in question-routes and TaskStops the replaced PI. | one defender per route prevents conflicting edits; the pointer keeps the chain of custody explicit. | rules/worker-lifespans.md |
| same-title review serialization | reviews of routes with the same title may run concurrently. | no two reviews of the same route title run concurrently; an in-flight challenge finishes before a handover starts. | same-title routes are versions of one thread; parallel reviews of them would produce inconsistent verdicts. | rules/worker-lifespans.md |

| formalizer agent cuts (2026-08-10) | the working swarm has ~8 workers; the lean runner's swarm is whatever the plan requires; decompose workers pair units freely. | the working swarm is ~4 workers; the lean runner's swarm is at most 3; at most one decompose pair runs at a time. | the Formalizer block is the largest constant agent cost; 4 workers with the relay still cover the mechanical qmd/lean transformation. | rules/formalizer.md |
| creator standard sizes from round 3 (2026-08-10) | n is chosen per phase, 0 ≤ n ≤ 8. | from round 3 the standard sizes are n = 2 per phase (phase 1: 2 idea workers; phase 2: 1 graph worker + 1 miner); rounds 1–2 keep 4+4; the 0–8 freedom stays. | fewer summaries suffice once the pool is rich; halves the Creator's agent cost in steady state. | rules/core-loop.md §1.2/§1.3 |
| producer single-writer lanes from round 3 (2026-08-10) | the Producer runs two phase-1 report writers plus the route lane. | from round 3 phase 1 runs exactly one report writer (one triple per round) and phase 2 exactly one route writer; at the Producer's start the phase-2 writer has 1 minute to choose 0 or 1 summary closest to its accepted route, and the Producer hands the remaining summaries to the phase-1 writer. | the reduced Creator (2+2) supplies 4 summaries per round — one triple plus the lane's choice — so a second phase-1 writer would starve. | rules/core-loop.md §2.2 |
| round total +1 from round 3 (2026-08-10) | the round is 138 minutes. | rounds ≥ 3 run 139 minutes: the Producer's 1-minute choice is added at the 20-min mark and the windows after it shift +1 (21–46, 46–64, 64–104, 104–119, 119–139); rounds 1–2 run 138. | the choice is a real step and is counted in the budget. | rules/timekeeping.md §4 |
| pi hygiene (2026-08-10) | a replaced PI closes after the handover. | hard invariant: the replaced PI is TaskStopped immediately at the handover and is never held open or resumed; only the current defender PIs of the accepted routes stay held. | held PIs are a steady cost; superseded ones carry no further duty. | rules/worker-lifespans.md |

| clock watcher (2026-08-10) | the Coordinator polls TaskList at each window end. | a pure background `sleep 120` spawned at round start wakes the Coordinator every 2 minutes: it computes the elapsed time, cuts every boundary that passed since the last recorded one, records the phase-time table, mirrors a current-status table into runtime/coordinator-state.md, and re-spawns the watcher; the watcher is a registered live worker and a missing one is re-spawned at the round-start check; each wake audits the previous wake's duty by file, and a wake delivered while the Coordinator is mid-turn is held and caught up on at the next turn boundary (the procedure is idempotent). | a turn that ends before a window end would otherwise leave the round silent until the user prompts; the watcher makes every window end wake the Coordinator even when its own turn ended earlier. | rules/timekeeping.md §6 |
| Coordinator turn discipline (2026-08-10) | the Coordinator never closes; the lifecycle contract (children-in-flight | awaiting-resume | closed) binds the subcoordinators. | the Coordinator's own turns now carry the same contract: every turn ends with a lifecycle line — children-in-flight (<task-ids>, <pending artifact paths>) | awaiting-resume at <window> | round-closed — written to runtime/coordinator-state.md, plus a pre-close audit that verifies by file that declared-done phases have their artifacts and restarts any current-phase worker that is neither done nor running; the round-start check resumes a mid-round phase from the state file before anything new. | a turn ending mid-round with nothing in flight froze the pipeline with no background tasks; the lifecycle line makes any resumed prompt (auto or user) resume the round from a file. | rules/coordinator.md §3, worker-lifespans.md |
| lean runner batching + run-or-postpone gate (2026-08-10) | the lean code runner is resumed on every qmd file update. | the runner is resumed once per round at the round start — batched, never on every qmd update; when landed-but-unintegrated per-fragment files exist (or the runner is recorded paused with pending units) and the runner is not already active, the Coordinator asks the user to run now or postpone to the next round; a postponed runner is recorded `paused: round N` (worker registry + the Formalizer's resume pack), is not resumed on any trigger, and the Formalizer re-requests it at the next round start, where the Coordinator asks again. | per-update resumes spawn a full LLM planning turn per fragment batch; batching to one resumption per round cuts the overhead and makes the postpone decision a single round-start question. | rules/formalizer.md, rules/coordinator.md §1 |
| lean runner auto mode (2026-08-10) | the lean-runner gate asks run-or-postpone at every round start. | a round-1 runner-mode question stands for the project: `auto` — the Coordinator resumes the runner automatically at each round start whenever pending lean work exists, without asking; `manual` (default) — the gate asks run-or-postpone each time, nothing else changes. | auto mode removes the recurring question for users who always want the runner working; manual keeps per-round control. | rules/coordinator.md §1, rules/formalizer.md |
| round auto-run to the chosen count (2026-08-10) | the user chooses the number of rounds; rounds stop at a milestone or when the user decides. | the round count (locked name) is the binding cap: the Coordinator records it at round-1 setup — runtime/coordinator-state.md (`rounds-chosen` / `rounds-completed`) and the dossier — and auto-starts each next round at the round close until the count is reached, stopping early only at a milestone (manuscript), the two-consecutive-0/3 steering stop, or the user's stop; the user's per-close decisions (seeing accepted routes, recycle/park, pairings) are presented at the close and never block the next round's start — an unaccepted route defaults to park until the user decides, and the Producer marks an accepted route a new version only after the user has seen it. | the round count lived only in the Coordinator's todo list, so the rounds never auto-ran: each close ended `round-closed` and the project waited for the user. | rules/coordinator.md §6a, .kimi-code/agents/coordinator.md |
| self-arming clock watcher (2026-08-11) | the clock watcher is a background `sleep 120` spawned at round start and manually re-spawned by the Coordinator on every completion; a missed wake leaves zero watchers. | the watcher is a recurring scheduled job on the engine's scheduler — `CronCreate("*/2 * * * *", <locked wake prompt>, recurring)` created at round start, self-arming by construction, deleted at the atomic round close (CronDelete); the Coordinator verifies it is live at every mid-round turn end and at the round-start check (CronList), re-creating it when missing (a 7-day-stale job included); the one-shot `sleep 120` remains only as a fallback for engines without a scheduler, guarded by the same turn-end liveness check. | a live round ran 34 minutes with zero watchers (round 2, Adam_question project): the one-shot sleep's completion went unprocessed during a burst of worker completions and nothing re-armed the chain. | rules/timekeeping.md §6, rules/coordinator.md §3/§5/§6, .kimi-code/agents/coordinator.md |
| quiet wakes (2026-08-11) | every wake opens with a current-status table shown to the user. | wakes stay quiet by default: the status table is shown to the user only when the wake did something real — a boundary cut, a stall repair, a worker completion since the last wake, or the round close — and is always mirrored into runtime/coordinator-state.md; a no-op wake writes one line (`wake <ts> no-op`) and ends without a user-visible table. the `*/2` cadence and the poll/cut/stall duty are unchanged; the canary is now event-driven (a broken chain surfaces at the next event wake or the next user prompt). | a table every 2 minutes is ~70 user-visible tables per round; the files are the recovery path, so visibility is not safety. | rules/timekeeping.md §6, .kimi-code/agents/coordinator.md |
